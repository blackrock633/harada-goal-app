# Mobile usability and accessibility review

Date: 2026-10-19. Scope: AppShell, primitives, globals.css, DESIGN_SYSTEM.md, DOMAIN_MODEL.md section 4-5. Evidence: static read plus Playwright/axe run in headless Google Chrome against a patched scratch copy of the app (see "Environment findings"). Paths are relative to the project root.

## Environment findings (block any testing of the real tree)
The unpatched tree does not render. In a scratch copy, these edits were needed before `next dev` served `/styleguide`:
1. `src/app/layout.tsx:17` `axes: ['opsz']` together with `weight: [...]` is rejected by next/font: every route (including `/api/health`) returned 500.
2. `src/ui/primitives/Tabs.tsx:1` uses `usePathname` without `"use client"`; `Dialog.tsx`, `Field.tsx`, `Input.tsx`, `Menu.tsx` use context/Radix without it. Server page importing the barrel `index.ts` crashes.
3. `src/app/(dev)/styleguide/page.tsx` is a server component passing function props (`signOutAction`, `onConfirm`) and calling `useToast`: needs `"use client"` (or extraction).
4. `/styleguide` calls `notFound()` when `NODE_ENV === 'production'` (page.tsx:13) and `playwright.config.ts` starts `next start` with `NODE_ENV=production`: styleguide E2E can never run under the stock config.

## Prioritised findings (severity x user impact)

1. **CRITICAL - App does not render on a clean checkout** (layout.tsx:17; Tabs/Dialog/Field/Input/Menu missing "use client"; styleguide page). Every route 500s in dev. Users see nothing; E2E cannot run. Fix the four items above; add a CI smoke test (`mobile-shell.spec.ts` covers `/api/health` and `/`).
2. **HIGH - Safe-area handling is a no-op.** AppShell.tsx:33 (`safe-top`) and :118 (`safe-bottom`) reference classes that exist nowhere (grep: only those two usages; test `bottom tab bar reserves safe-area inset` fails). The root layout also sets no `viewport-fit=cover`, so `env(safe-area-inset-*)` would be 0 even if defined. On iPhone the fixed tab bar (AppShell.tsx:118) sits on the home indicator and the top bar under the notch/Dynamic Island in standalone mode. Fix: `export const viewport = { viewportFit: 'cover' }` and define `.safe-top{padding-top:env(safe-area-inset-top)}`, `.safe-bottom{padding-bottom:env(safe-area-inset-bottom)}`; make tab bar height and `main` bottom padding (`pb-20`, AppShell.tsx:107) account for it, e.g. `pb-[calc(5rem+env(safe-area-inset-bottom))]`.
3. **HIGH - Touch targets below 44px on mobile, contradicting DESIGN_SYSTEM.md:§5 ("min touch target 44 px on mobile").** Measured at 390 and 360 wide: Button md 40px high, sm 32px (Button.tsx:17), Input/Select/DateInput 40px (Input.tsx:17,79,101), toast Close ~22x22 (Toast.tsx:95), toast action 32px (Toast.tsx:87), user-menu avatar button 32x32 (AppShell.tsx:38; the only account/sign-out entry on mobile), Tabs links ~py-3 text-sm. `min-w-[44px]` was applied but not min-height. Fix: `min-h-[44px]` below `md`, or invisible hit-area padding. Test `interactive elements are at least 44x44` is marked DEFECT/test.fail.
4. **HIGH - Misleading progress and pace (DOMAIN_MODEL.md:§4.3-4.5).** (a) "Progress" is action completion, but the goal is attainment of a result. A goal reaching 100% progress is not "achieved" (separate `markGoalAchieved`), yet one ring/bar labelled "Progress" will be read as attainment. Label it "Plan completed" / "Actions done" and show attainment (measure current/target) separately. (b) `goalProgress` is the mean of non-null outcomes (4.4): an outcome with no actions is `null` and silently dropped, so one outcome with one completed task yields 100% while seven outcomes are empty. Need a "plan completeness" figure (x of 64 slots filled) and treat unmeasured outcomes as visible gaps, not omissions. (c) An outcome with a `measure` (current/target) is averaged with outcomes derived from action counts, mixing results with effort. (d) Pace (4.5) compares action completion to elapsed calendar time; "Ahead" (badge success green) says the user is ahead on the goal when only task ticking is ahead. Doing easy tasks first shows "Ahead". Suggest: pace badge text "Actions ahead of schedule", never shown when progress is null or the plan is empty, no green when no outcome is measurable. (e) The word "Overdue" is used for both a task and a goal pace (4.5 / DESIGN_SYSTEM Badge), which will collide on the same screen.
5. **HIGH - Colour/opacity-dependent state and axe contrast failures.** Axe (serious, light): 4 colour-contrast nodes; dark: 2. Completed rows use `opacity-60`/`opacity-50` + `line-through` (styleguide/page.tsx:186-208) giving 2.49-4.13:1; sample cell `text-accent-ink` on `accent-soft` is 1.25:1 (page.tsx:205), a hazard for the planned grid cells. Active nav and CheckCircle state rely on colour (accent) plus a fill change (CheckCircle.tsx:29-32 does have an icon for tasks, but routines show `↻` in both checked and unchecked states, differing only by colour/fill). Add a distinct checked glyph for routines and do not fade text with opacity; use a token.
6. **HIGH - ProgressRing has no accessible name** (Progress.tsx:50-56; axe serious `aria-progressbar-name`, 3 nodes; ProgressBar does set `aria-label`, line 27). Add a `label` prop and `aria-label`. Also the redundant `sr-only` text inside a progressbar (Progress.tsx:29,57) may double announce.
7. **MEDIUM - Fixed bottom tab bar versus the keyboard and toasts.** Tab bar is `fixed bottom-0` (AppShell.tsx:118). On iOS Safari the fixed bar rides above the keyboard only partially; on Android with `interactive-widget` default, the layout viewport does not shrink, so an editor field near the bottom is covered by the keyboard and the bar. Add `interactive-widget=resizes-content` in viewport, hide the tab bar while a text field is focused, and scroll-padding-bottom on `main`. Toasts are `fixed top-0` on mobile (Toast.tsx:48) and will cover the sticky top bar (z-40 vs z-[100]) and its menu button; for an Undo action (DESIGN_SYSTEM.md:§7) that is auto-dismissed in 4s (Toast.tsx:62), the timing is also too short for screen-reader and motor-impaired users (WCAG 2.2.1); pause on hover/focus and allow longer for actionable toasts. `aria-live="polite"` is on the container but each toast also has `role="status"`; fine, but errors should be `role="alert"`.
8. **MEDIUM - Viewport units and text scaling.** `min-h-screen` (AppShell.tsx:30) and `h-screen` on the rail (:51), `max-h-screen` toast container (Toast.tsx:48): on mobile Safari 100vh includes the collapsed toolbar area, causing scroll jank; use `min-h-dvh`/`h-dvh`. Dialog is vertically centred with no max-height or scroll (Dialog.tsx:19): at 360x640, with keyboard or 200% text, long content is unreachable; add `max-h-[calc(100dvh-2rem)] overflow-y-auto` and bottom-sheet behaviour on mobile. Buttons use fixed heights `h-[40px]` (Button.tsx:17) so text zoom/larger Dynamic Type clips text; use `min-h` instead. `text-xs` (12px) is used for tab labels (AppShell.tsx:125), badges (Badge.tsx:32), counters; design doc says 12px is "meta only" but tab labels are interactive labels.
9. **MEDIUM - Focus management.** Visible focus works (test passes; `:focus-visible` outline in globals.css plus ring utilities), but: the skip link targets `#main-content` which is rendered only by AppShell (layout.tsx:43; routes without the shell get a dead link); the `ring-accent` on dark `bg-accent` buttons has no offset so it is invisible on the button itself (Button.tsx:16 `focus-visible:outline-none focus-visible:ring-2` replaces the 2px offset outline promised in DESIGN_SYSTEM.md:§7); after route changes, focus is not moved to `main`/h1 (main has `tabIndex={-1}` but nothing focuses it); "focus moves to first invalid field" (§7) is not implemented in Field/Input; Menu sign-out calls `signOutAction()` with no pending/error state (AppShell.tsx:47).
10. **MEDIUM - Today list and the 64 matrix versus daily execution.** (a) `nextActions` (DOMAIN_MODEL.md:§5) returns an unbounded list: routines first, then tasks. With up to N goals x 64 actions, "Today" can be 30+ rows with no "start here" and no cap; add a default top-3/5 "focus" and a collapsed "More". (b) Routines due today precede an overdue task, so a user with a three-week-old overdue task sees it below routines; ordering should be stated and reviewable. (c) No time-of-day, no snooze/skip, no way to record "did not do, because...", so a missed day only silently reduces adherence. (d) Weekly(N) routines are "due today" every day until N met (§5), which fills Today daily with an item that is optional on most days. (e) Check-in for past days is only in the monthly sheet, but forgot-to-tick-last-night is the common case; offer "yesterday" in Today. (f) Mobile 64-grid accordion (DESIGN_SYSTEM.md:§6) is sound: 8 accordion sections x 8 rows, but it loses the at-a-glance gaps view that is the Harada method's point; show per-outcome "x/8 actions" counts and a plan-completeness summary at the top. Accordion triggers must be 44px and keep open state across edits. (g) 9x9 below 1024px must not be shrunk; tablets (768-1023) fall into the accordion, which is fine, but keyboard arrows are desktop-only: ensure the accordion has proper `aria-expanded` and heading structure.
11. **LOW - Other.** AppShell has two `<nav>` landmarks visible to AT only one at a time (lg:hidden vs hidden lg:flex use `display:none`, fine); desktop rail marks Settings active but not `aria-current` (AppShell.tsx:81-92); mobile top bar has only an avatar button with sr-only label and no page title; `bg-paper/90 backdrop-blur-sm` contradicts "never glassmorphism" (DESIGN_SYSTEM.md:§1) and makes text contrast dependent on content scrolling beneath; `animate-in` utilities (Toast.tsx:71, Menu.tsx:17, Dialog.tsx:15) require the tw-animate-css/plugin: not imported in globals.css, so animations are likely no-ops (verify).

## What worked (verified in browser)
No horizontal overflow at 360x640 and 390x844 on `/` and `/styleguide`; tab bar does not cover the final content (pb-20 holds at these sizes); focus indicator is visible on Tab; `/api/health` returns 200 `{"status":"ok"}`.
