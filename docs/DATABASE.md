# Database — Harada Goal App

> **Status: CANONICAL.** The schema of record is the SQL in `supabase/migrations/` (tables, constraints,
> triggers, RLS policies). `src/infrastructure/db/schema.ts` is a Drizzle **mirror** used to type queries;
> `schema-sync.test.ts` fails if the two drift. Domain concepts: `DOMAIN_MODEL.md`. Decisions: D-013, D-014.

## Engine and environments

| Environment | Database | Auth |
|---|---|---|
| Production / staging | Supabase Postgres (`DATABASE_URL` = pooler, transaction mode) | Supabase Auth |
| Local dev (no Docker) | PGlite `pglite://.data/dev` + `supabase/tests/auth-shim.sql` | `AUTH_PROVIDER=dev` (dev-only gateway) |
| Local dev (with Docker) | `supabase start` → its Postgres URL | Supabase Auth (local) |
| Tests | in-memory PGlite + shim + all migrations | `FakeAuthGateway` (test double) |

The shim emulates Supabase's `auth` schema, the `anon` / `authenticated` / `service_role` roles and
`auth.uid()`, so **RLS, constraints and triggers run for real in tests**. GoTrue (password checks, JWT
issuing) is not emulated. It is never applied to a real Supabase project.

## Conventions

- `snake_case` tables/columns; Drizzle maps to camelCase. Primary keys are `uuid`, generated by the app
  (which also makes creates idempotent: a retried create with the same id doesn't duplicate).
- `timestamptz` for instants; `date` for local calendar dates (`'YYYY-MM-DD'`, user's time zone).
- FK deletes cascade from parent to child; reached only via permanent goal delete or account deletion.

## Tables

### `profiles` (1:1 with `auth.users`)
`id uuid pk → auth.users(id) on delete cascade`, `display_name text (1..80)`, `time_zone text default 'UTC'`,
timestamps. Created by trigger `on_auth_user_created` from sign-up metadata
`{display_name, time_zone}` (sanitised: blank name → email local-part, unknown zone → UTC).
Email and credentials stay in `auth.users` and are never copied.

### `goals`
`id`, `owner_id → profiles(id) cascade`, `title (1..120)`, `vision (≤2000)`, `success_criteria (≤2000)`,
`target_date`, `status ∈ draft|active|achieved|archived`, `status_before_archive`, four `purpose_*`
quadrants (≤1000 each), `activated_on`, `achieved_at`, `archived_at`, timestamps.
Checks: archive consistency; `achieved_at` only when achieved/archived.
Index: `(owner_id, status)`.

### `outcomes` (the 8 key areas)
`id`, `goal_id → goals cascade`, `title (1..120)`, `description (≤1000)`, `measure_target/current/unit`
(all null, or all set with target > 0, current ≥ 0, unit ≤ 24 chars, unit may be `''`), `position`,
`archived_at`, timestamps.
- `position` ∈ 0..7 while active, `null` while archived.
- **Exclusion constraint** `outcomes_goal_position_excl (goal_id =, position =) WHERE archived_at IS NULL`,
  `DEFERRABLE INITIALLY IMMEDIATE`. It makes active positions unique, and together with 0..7 caps active
  outcomes at 8 even under concurrency.
- `unique (id, goal_id)`: target of the actions composite FK.

### `actions` (8 per outcome)
`id`, `goal_id → goals cascade`, `outcome_id`, `title (1..160)`, `notes (≤2000)`, `kind ∈ task|routine`,
`position`, `due_date`, `completed_at`, `schedule_type ∈ daily|weekdays|weekly`, `schedule_days smallint[]`,
`schedule_times_per_week (1..7)`, `start_date`, `archived_at`, timestamps.
- **Composite FK** `(outcome_id, goal_id) → outcomes(id, goal_id) on delete cascade`: an action can never
  point at an outcome in a different goal.
- Same 0..7 / exclusion-constraint scheme per outcome (`actions_outcome_position_excl`).
- Check: schedule shape matches `schedule_type`; tasks have no schedule; routines have schedule + start
  date and no due date / completion.
- Indexes: `goal_id`, `outcome_id`.

### `routine_checks`
`id`, `action_id → actions cascade`, `date`, `created_at`. `unique (action_id, date)`; inserts are
`ON CONFLICT DO NOTHING` (idempotent check).

### `reflections`
`id`, `goal_id → goals cascade`, `date`, `kind ∈ daily|weekly`, three text fields (≤4000), timestamps.
Index: `(goal_id, date desc)`.

### `goal_events` (history)
`id`, `goal_id → goals cascade`, `type`, `subject_id`, `summary`, `data jsonb`, `occurred_at`.
**Append-only**: no UPDATE/DELETE grant or policy. Completions and reopenings are recorded here, which is
the activity history (no event sourcing; current state lives in the entity tables).
Index: `(goal_id, occurred_at desc)`.

## The matrix (1 + 8 + 64)

- The central goal is the `goals` row. Key areas are `outcomes` at positions 0..7. Actions are at
  positions 0..7 within each outcome.
- **Empty cells are absent rows.** Nothing is pre-created and no placeholder content is stored. A new
  goal is a valid, empty matrix. "Initialization" is therefore just creating the goal (or a goal from a
  template, which inserts the goal + outcomes + actions in **one transaction**).
- The application maps rows onto fixed arrays: `getGoalDetail().matrix.outcomes[0..7]`, each with
  `slots[0..7]`, with `null` for empty positions (see `src/application/dto.ts`).
- Repeat safety: creates carry a client-generated uuid; a replay returns the existing row instead of
  inserting a second one. Positions are protected by the exclusion constraints, so a duplicate or
  concurrent add to a taken slot fails with `CONFLICT` and never overwrites.
- Reorders run in one transaction: `SET CONSTRAINTS … DEFERRED`, then write the final positions; uniqueness
  is checked at commit.

## Security model (RLS)

RLS is enabled on **every** table (a test fails if a new table lacks RLS or policies).

| Table | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| profiles | own | trigger only | own | via auth.users cascade |
| goals | `owner_id = auth.uid()` | same | same (`with check` blocks re-owning) | own **and** `status='archived'` |
| outcomes, actions, reflections | `owns_goal(goal_id)` | same | same (with check) | same |
| routine_checks | `owns_action(action_id)` | same | — | same |
| goal_events | `owns_goal(goal_id)` | same | — (append-only) | — |

- `anon` has no table grants. `owns_goal` / `owns_action` are `SECURITY DEFINER` and `STABLE` with an
  empty `search_path`. They only answer "does the current user own X". Policies wrap calls in
  `(select …)` so Postgres evaluates them once per statement, not per row.
- **Server path:** `UnitOfWork.run(userId, fn)` opens a transaction, `SET LOCAL role authenticated` and
  `request.jwt.claims = {"sub": userId}`. The same policies therefore govern server-side Drizzle queries
  and any future supabase-js client (e.g. a mobile app) using the user's JWT. `userId` comes only from
  `supabase.auth.getUser()` (server-verified).
- Repositories still scope by owner (defence in depth). A row owned by someone else reads as `NOT_FOUND`.
- The service-role key is used only server-side for account deletion. It never ships to a client.

## Migrations

- Versioned, forward-only SQL in `supabase/migrations/<YYYYMMDDHHMMSS>_<name>.sql`.
- Real databases: `supabase link --project-ref <ref>` then `supabase db push` (see `SUPABASE_SETUP.md`).
- Local PGlite: applied automatically by `applyLocalMigrations()` (tracked in `app_meta.schema_migrations`).
- Never reset or drop user data to resolve a conflict. Data-changing migrations must carry their own
  data-preserving step.
- History: `drizzle/0000_init.sql` (pre-Supabase) was retired by D-013. It had only been applied to local
  dev/test PGlite databases. Delete old `.data/dev` after pulling (`rm -rf .data/dev`). It contains no
  real user data and has the old schema.

## Deletion policy

| Entity | User-facing | Mechanism |
|---|---|---|
| Goal | Archive (reversible); permanent delete only from archived (enforced by RLS) | soft → hard |
| Outcome / Action | Archive / restore | soft |
| RoutineCheck | Uncheck | hard |
| Reflection | Delete with confirmation | hard |
| Account | Re-authenticate + typed confirmation → `auth.admin.deleteUser` | hard cascade |
